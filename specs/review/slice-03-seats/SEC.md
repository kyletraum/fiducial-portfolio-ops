### On the three write layers (the charge's "redundant, complementary, or conflicting")

Complementary, with one conflict found and fixed above (SEC-6). Layer 1 (content types that force a preflight the API never answers) and layer 2 (`Sec-Fetch-Site`) are both *browser-behaviour* defences: they hold only because the browser refuses to send, or marks, the request. The antiforgery token is the only layer that does not depend on the browser volunteering metadata (**INFERRED**: Safari gained Fetch Metadata only in 16.4). With `SameSite=Strict` the session cookie is still sent from another `localhost` port, because a site ignores ports — slice 02's browser test already showed `localhost`-to-`localhost` as same-site (`EXECUTED` by slice 02) — so Spike J claim 3 is right and the token is doing real work there. The antiforgery cookie's own `SameSite=Strict` default is fine. No layer replaces another; SEC-1 is what makes the third layer exist at all.

## Axis 2 — scope, buildability, teaching value

**Scope.** The slice is coherent: one technique, carried through every layer, and Kyle's four additions are each small except the CSP (Spike K's problem) and first-run enrolment (SEC-4, which is a design question the slice correctly leaves open — but it should be closed before step 1, not during it). Nothing the slice adds is foreign to `security.md`; the `sessions` table is the one new object, and SEC-5 gives it a job. "CORS grants nothing" is stricter than `security.md`'s "restricted to the known frontend origin" and is the right correction for a same-origin app. The pre-commit hook is owed (`D-030`), not scope creep.

**What the slice drops, quietly.** Data-mutation audit and the no-credential-in-responses contract test (SEC-13); the non-superuser role (`security.md` "Database") is outside the commissioned sections but the audit table's immutability claim leans on it (SEC-8). Recording deferrals is cheaper than discovering them at the assessment.

**Buildability.** The hard parts are in steps 1–3, in this order: the Identity store shape (an EF migration of `Version3`'s passkey tables on Npgsql was not run — `RESULTS.md` says so); the antiforgery refusal that the framework does not provide (SEC-1); the limiter's shape (SEC-3); the setup-code channel (SEC-4). Everything else is configuration with a test. The E2E for "each layer refusing on its own" needs no test-only switches: slice 02's integration pattern (`CrossSiteWriteTests`: a request that one layer admits, refused by the other) extends to the token — a request with a valid session, `Sec-Fetch-Site: same-origin`, an accepted content type and no token must be `403`. For Spike K, Vite's `html.cspNonce` exists (`DOCS`) and generates a nonce for injected script/style tags, which is the dev-policy escape hatch the spike is looking for; `frame-ancestors` only works as a header, never in `<meta>`, so the dev policy belongs in `server.headers` and the published one in a middleware ahead of `UseFileServer`.

**On Spike H.** The result is sound and the "found on the way" items are the valuable kind (EF in-memory cannot read passkeys back; cookie auth redirects). Two things to carry into step 1 that the spike could not see: Identity enforces user verification by default and checks the sign counter (good; keep both visible), and the lockout interplay of SEC-2. The argon2id comparison is well done; the parameter choice is defensible and `NeedsRehash` → `SuccessRehashNeeded` is the right wiring.

**Teaching value** (the gate's techniques limb, for Kyle's judgement, not mine): three candidates this slice can genuinely demonstrate with a commit each — (1) WebAuthn end to end with a CDP virtual authenticator in CI, with no library; (2) CSRF in an SPA where the framework validates but the application must refuse, bound to identity and refreshed on sign-in (SEC-1, SEC-7 — a lesson most tutorials get wrong); (3) budgeting a memory-hard hash against a container limit with a concurrency limiter rather than a rate limiter (SEC-3). The audit table and the pre-commit hook are chores, not techniques, and the assessment should not count them.

**Not a defect, worth saying.** The threat model's out-of-scope line ("a compromised host with an active attacker at the keyboard") is doing a lot of work in this slice. Every control here distinguishes *Kyle's browser* from *a page in Kyle's browser* and from *a process without his console*; none can distinguish Kyle from a process running as Kyle. The slice should say that in one sentence, so the assessment's "which attacks were shown refused in a real browser, and which only argued" has an honest denominator.
