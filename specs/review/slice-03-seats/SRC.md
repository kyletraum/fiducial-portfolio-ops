## Axis 2 — scope, buildability, teaching value

**Scope.** Taking Identity's in-box passkey handler with no WebAuthn library is well supported by the source: the handler implements the registration and assertion ceremonies step-by-step against the Level 3 spec (`PasskeyHandler.cs` comments cite each step), with fixed-time comparisons, UP/UV/BE/BS checks, and the sign-count rule. What it leaves to the application is exactly what this design has to own anyway: the RP ID (SRC-2), the expected origins (SRC-3), attestation policy (none, which is right here), and the enrolment gate (SRC-11). The argon2id choice is orthogonal to the framework; the only framework fact that matters is that `IPasswordHasher<TUser>` is a clean seam and rehash-on-login is honoured (F21).

**Buildability.** Two places where the framework gives less than it appears to, and the design's outline currently assumes the appearance: antiforgery on minimal APIs (SRC-1: the middleware records, it does not refuse) and "sessions" (SRC-6: a table is not a session unless it backs `ITicketStore`). Both are small to build once named, but each would otherwise be discovered in step 3 or step 1 as a surprise, and SRC-1 would be discovered only by a test that fails to fail. The rest of the tier (fallback policy, `DisableCookieRedirect`, rate limiter policies, data-protection persistence) is configuration the framework already has; the design re-implements some of it (an architecture test instead of a fallback policy; an `OnRedirectToLogin` override instead of endpoint metadata), which works but hides the framework's own switches from the reader. The published stack adds two deployment facts the slice did not plan for, forwarded headers (SRC-9) and the key ring (SRC-10); neither blocks, both bite on the first `docker compose up` after a rebuild.

**Teaching value.** Measured against the gate's "techniques Kyle did not already have", the framework reading itself yields candidates the outline does not name: `ITicketStore`-backed sessions versus self-contained tickets and what revocation means under each; the antiforgery feature/metadata model and why a SPA has to validate explicitly; the `FallbackPolicy` + `AllowAnonymous` inversion; the data-protection key ring as the real root of trust for cookies in a container. Each is demonstrable in one commit with a test that fails without it. Conversely, "security headers and CSP" and "CORS grants nothing" are configuration, not technique, and CORS in particular is not a refusal layer (F20); the assessment should not count them.

**One sentence on the spike.** Spike H answered its three claims honestly and found two true things on the way (in-memory, redirect); what it did not read is the handler's `GetServerDomain` and `ValidateOriginAsync`, which is where the `127.0.0.1` result actually comes from and where the slice's "origin validation" claim has to be made true by configuration rather than assumed from the option list.
