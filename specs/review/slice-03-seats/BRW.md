## Method

1. **Specs, read, not recalled.** The editor's drafts of WebAuthn Level 3, CSP Level 3, Fetch, RFC 6265bis (draft-ietf-httpbis-rfc6265bis), HTML "origin/site", Secure Contexts and Fetch Metadata were downloaded to the scratch area on 2026-10-21 and grepped for the exact passages quoted below. MDN `browser-compat-data` 8.1.6 (`@mdn/browser-compat-data@latest`, unpkg) supplied first-shipped versions.
2. **A Playwright probe, executed.** `…\scratchpad\brwprobe\probe.mjs` (results in `result-chromium.json`, `result-firefox.json` beside it). It starts three real loopback listeners: **A**, "the app" (sets eight cookies of differing attributes; echoes every request header it sees into a server-side log; serves a page under a strict CSP; serves `/frame` with `frame-ancestors 'none'` as a header and `/frame-meta` with it in `<meta>`); **B**, "the attacker", one page answering any `Host`; and **the repository's own Vite 8.3.4 + `@vitejs/plugin-react` 6.1.2** (via a junction to `web/node_modules`, `server.cors:false`, `/api` proxied to A with `changeOrigin:true`, as `web/vite.config.ts` does), rendering a Recharts 3.10.1 `LineChart` and `ResponsiveContainer` with a `.css` import, as `web/src/main.tsx` does. It then runs: the app page at `http://localhost`, `http://127.0.0.1` and `http://app.localhost` (cookies, secure context, the WebAuthn JSON API, a 5-value `rp.id` matrix against a CDP virtual authenticator); the attacker from `localhost:B` (same-site), `attacker.localhost:B` and `127.0.0.1:B` (cross-site) against A and against the Vite proxy (13 fetch variants, two form posts, an `<img>`, two iframes, a top-level link click), recording both what the page saw and what the server saw; the Vite dev page under no CSP, a strict CSP, and `html.cspNonce`; and a `vite build` served by A under the strict CSP. **Browsers: Chromium 153.0.8010.12** (Playwright 1.63's bundled build, the one `tests/E2E` uses) **and Firefox 155.0** (`playwright install firefox`, ~1 min). Invented data only; no repository file was written.
3. **Markers.** `EXECUTED` = observed in the probe above, both browsers unless one is named. `SOURCE@` = read in package or reference-assembly source on disk. `DOCS@2026-10-21` = read in the cited specification or documentation. `INFERRED` = reasoned, not observed; every load-bearing one is a gate.

Spike H's result is confirmed, not repeated: the driver in `spikes/spike-h-auth/SpikeH.Driver/Program.cs` and my probe use the same CDP `WebAuthn.addVirtualAuthenticator` route, and both saw `This is an invalid domain.` on `127.0.0.1`.

## Gates

Load-bearing claims this seat could not raise above `INFERRED`:

- **G1 — the proxy target host.** `web/vite.config.ts` proxies to `API_HTTPS || API_HTTP`; with `changeOrigin:true` the API's `Host` is that URL's host (EXECUTED). Whether Aspire injects it as `localhost:<port>` or `127.0.0.1:<port>` was not observed (no `aspire run` under the ground rules). The passkey path through the proxy is therefore **INFERRED** until the E2E runs it; BRW-3 removes the dependence by pinning `ServerDomain`.
- **G2 — `Sec-Fetch-Site: none` from non-web initiators.** `CrossSiteWrites` allows `none`. The spec reserves `none` for user-initiated navigations (DOCS), which cannot `POST`; whether Chromium/Firefox also send `none` for requests initiated by **extensions** (which the slice names as a threat) is INFERRED, not observed. The CSRF token, not layer 2, is the defence for that case; say so.
- **G3 — HMR under the dev CSP.** My dev policy allowed `connect-src 'self' ws: http://localhost:*` and saw no violation, but did not assert that the HMR socket connected. INFERRED that `ws:` (or `ws://localhost:*`) is required; Spike K should watch the console with it removed.
- **G4 — emitted cookie attributes.** F6/F8 are browser facts; the defaults in BRW-1/BRW-2 are read from the 10.0.13 reference documentation, not observed on this API. Step 2's first `Set-Cookie` settles it.
- **G5 — Safari.** Reports that Safari rejects `Secure` cookies on `http://localhost` (web search, not executed, not a target browser). 6265bis makes "secure" a user-agent definition, so the slice's "no TLS on loopback" design is a two-browser design; record it as such.

## Axis 2 — scope, buildability, teaching value

**Scope.** Everything the browser must do for this slice, it does on `http://localhost` without TLS, in both target browsers: secure context, RP ID `localhost`, `Secure`/`__Host-` cookies, Strict same-site semantics, Fetch Metadata, a strict published CSP with Recharts intact. No scope change to Kyle is warranted on browser grounds; Spike I's "does the published stack need TLS" can be answered **no** now, from EXECUTED evidence. The one real narrowing is F9: the app must be reached as `localhost`, so `127.0.0.1` and `[::1]` should leave `AllowedHosts` rather than stay as a half-working alias.

**Buildability.** Three sharpenings (BRW-1 to BRW-4) are each a line of configuration, and all are discoverable in the first hour of step 2 or 3 — but discoverable as a *mysterious* failure (a passkey that registers and never asserts; an unstyled dev page; a `__Host-` cookie the browser drops). Naming them in the spike results converts debugging into checklist. The browser-facts probe is ~250 lines of plain Node + Playwright with no app dependency; lifted into `tests/E2E` as a "browser facts" test it would pin F6–F8, F10, F12 and F13 in CI for the price of one Firefox download, and make DoD 1's "restated at EXECUTED" literal.

**Teaching value.** Two facts carry the slice's whole three-layer argument and are easy to show: *ports are not sites* (a Strict cookie walks straight across them, F7) and *`no-cors` rewrites or drops your `Content-Type`* (F12). Both are more convincing from a server log than from a spec quotation, and the probe produces exactly that log. The CSP work teaches a third: the published policy is simple because React writes styles through the CSSOM, and the dev policy is complicated because Vite writes HTML — a distinction worth a sentence in Spike K rather than a `'unsafe-inline'` left "for dev".
