Slice 03 (`specs/001-portfolio-platform/slice-03.md`, branch `slice-03-spike-h` at `f3b5c2b`): login (passkey, password fallback), first-run enrolment, logout, session expiry, every page behind a session. Reviewed against WCAG 2.2 AA, the repository's floor (every E2E runs axe with `wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa`), and against how the existing pages are built.

**Fetched today (DOCS@2026-10-21):**
- WCAG 2.2 §7 "Input Purposes for User Interface Components" — https://www.w3.org/TR/WCAG22/#input-purposes — contains `username`, `new-password`, `current-password`; it does **not** contain `one-time-code`.
- Understanding 3.3.8 — https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html — "cognitive function test" includes "transcription, such as typing in characters" and memorisation of a password; "Copy and paste can be relied on to avoid transcription"; "it must be possible for a user to at least paste the code"; "A website uses WebAuthn so the user can authenticate with their device instead of username/password" is an example that passes; "This success criterion is focused on authentication of existing users" and "does not cover creation of a username or initiation of an account".

**Reading of the slice.** The web step (step 4) is an outline: "Login and enrolment pages, logout, an expired session sending the viewer to log in without losing the page". Nothing in the slice yet says where focus goes, what is announced, how long a session lives, what a throttled login says, or how the setup code travels from the console to the page. Those are the places where an AA failure is designed in before a line is written, and where axe would say nothing. The findings below are therefore mostly design requirements with the step they must precede, plus the test assertions that would catch them.

5. **Before step 7 claims DoD 6:** the DoD rewording in A11Y-11, with the dark-scheme context, the CSP/`BypassCSP` separation, and the virtual-authenticator presence and user-verification toggles in the test. "axe still 0" alone does not pass this seat for the slice's new behaviour.

Both take one Playwright line each to observe.

## Axis 2 — scope, buildability, teaching value

**Scope.** Everything above fits the slice as commissioned; nothing asks for a new feature. The one real scope choice is A11Y-2: option (a) is a configuration line and a sentence on the login page; option (b) is a timer, a banner, a renew endpoint and their tests. For a single-user loopback app whose cookie never leaves the machine, (a) is the honest answer, and it should be written down as a 2.2.1 decision rather than left as a default `ExpireTimeSpan`. Resist the temptation to build (b) for its own sake; it is the kind of code that is cut from a slice assessment later.

**Buildability.** The web work follows patterns the repository already has and tests: `Field`/`FormError` for every input and refusal, `role="status"` for every outcome, the Tab loop and `GetByRole(Status/Alert)` assertions in `tests/E2E`. The new pieces are small and generic: a `<dialog>` for expiry, a `focusHeading()` helper on view switches, an `onResponse` middleware for 401, and `aria-disabled` instead of `disabled` while a ceremony is in flight. The test side is where the cost sits: the virtual authenticator's `automaticPresenceSimulation` and `isUserVerified` switches turn "the passkey works" into "the page behaves when it does not", which is the half of DoD 3 that matters to this seat, and they cost two CDP calls each.

**Teaching value.** Three things this slice can teach that slices 01 and 02 did not, in this seat's area:
- **Focus management in a single-page app under async authentication**: where focus goes when the browser takes it (the passkey sheet) and gives it back, when a view replaces another, when a modal opens over preserved state, and when a session dies in the background. Slice 01 taught Tab order; this teaches the return path.
- **Testing what axe cannot**: asserting announcements and focus targets in Playwright, driving a WebAuthn ceremony into its pending and failing states with the CDP virtual authenticator, and separating "works under CSP" from "axe is clean" so the two do not quietly cancel each other.
- **WCAG as a design input rather than a floor check**: 2.2.1 deciding a session lifetime, 3.3.8 deciding how a setup code travels from a console, 1.3.5 deciding three attributes a password manager depends on, and WebAuthn §15.1 citing WCAG back at us for the ceremony timeout. Each is a line in a design note with a criterion number beside it, which is the habit the gate's "techniques" limb could count.

**Preferences (not defects), for the record:** passkey button above the password form, both always visible (no disclosure hiding the fallback); the "Signed out" dialog closable with Escape; no "confirm password"; the password rule stated as one plain sentence; the footer's health line left exactly as it is, since it is the one status that stays true through every authentication state.
