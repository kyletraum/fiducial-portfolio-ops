The marker rule (brief rule 1) was applied to the claim a severity rests on, not to the whole finding. Seven findings had their severity-bearing external claim at INFERRED or unmarked: those claims are now gates (G-7, G-8, G-2, G-28, G-29) and the findings stand on their marked remainder, with the severity lowered where the remainder does not carry it (RED-8's replay path, NOTE in C3-39). Confirmation counts are the number of seats that reached the same defect independently (the same defect, not a related one); seat IDs are listed with each. An item reached by three or more seats is treated as established, not as a matter of judgement. Axis 1 (below, with severity) holds defects only. Where a seat left something to the owner, it is in "Decisions for the owner" with the options and costs as the seats stated them. ## The headlines

**C3-1 — ASP.NET Core's antiforgery validates but never refuses on this API's endpoints** (BLOCKING; reached by 2 seats, SRC-1 and SEC-1; SOURCE@). `AntiforgeryMiddleware` runs only for POST/PUT/PATCH, only for endpoints carrying `IAntiforgeryMetadata`, which minimal APIs infer only for form-bound parameters, and on failure stores the result in a feature and calls `next`. Every platform write binds JSON or reads a raw body, so step 3's "antiforgery per Spike J on every unsafe method" would produce a third layer that validates and then lets the write execute, with DELETE never validated at all. Spike J claim 2 is false as the framework ships. The slice must own the refusal (an endpoint filter on the `/api` group), and Spike J must run a JSON endpoint, the raw-body upload and a DELETE with the header absent and see each refused.

**C3-2 — DoD 4 cannot be shown in a browser as written** (MUST FIX before step 3; reached by 4 seats, RED-4, TST-1, SCO-1, BRW-6; EXECUTED). With `UseCrossSiteWriteRefusal` first in `Program.cs`, every same-site browser write is refused by `Sec-Fetch-Site` (or never sent, by CORS preflight) before any token is read. "The browser test shows the CSRF token refusing the write" is green while the token has refused nothing. The DoD must be split: the token alone at the integration layer with a valid session, `same-origin`, an accepted content type and no token; the three layers together in the browser, each refusal identified by its `ProblemDetails.title` and the cookie proven sent.

**C3-3 — The first-run setup code is a sketch with no channel in the published stack and three open holes** (MUST FIX before step 1; reached by 7 seats, SEC-4, RED-5, OPS-4, SCO-2, SRC-11, A11Y-7, TST-3; EXECUTED). The published stack has no AppHost and no dashboard (`WithDashboard(false)`), so "shown in the AppHost's console" is `docker compose logs api`, which DoD 7 forbids a secret to reach. Strength, single use, expiry, constant-time comparison, atomicity of user-plus-first-credential, and what `/enrol` answers once a user exists are all unstated. Every candidate channel is readable by the one account that runs everything (OPS: `docker-users` has exactly one member), so the slice's "must not leave a window in which any local process can claim the account" must be reworded to a bounded, attested window. The mechanism is the owner's (D2).

**C3-7 and C3-8 — the login throttle must bound hashes in flight, not requests per minute, and Identity's lockout must not gate the passkey** (MUST FIX before step 3 and step 2; reached by 6 seats and 2 seats; EXECUTED + SOURCE@). Each argon2id verify holds 64 MiB of native memory outside the GC's 75 % cap; under the measured 234.5 MiB import peak, four concurrent verifications reach the 512 M cgroup limit and the container is OOM-killed, which `unless-stopped` turns into a loop. A window limiter admits N requests in the same 150 ms; a global `ConcurrencyLimiter` is what bounds them, and on loopback every caller shares one address so a per-IP partition keys on nothing (and, in compose, on attacker-chosen text: C3-9). Separately, `PasskeySignInAsync` runs `PreSignInCheck`, so with Identity's default lockout five wrong passwords from any local `curl` lock the passkey too, every five minutes, forever.

**C3-5 and C3-6 — "sessions" is undefined, logout does not revoke, and no cookie is `Secure` or `Strict` unless configured** (MUST FIX at step 1 and step 2; reached by 4 seats each; SOURCE@ and EXECUTED). Identity's cookie is a self-contained 14-day sliding ticket; `SignOutAsync` deletes the browser's copy and nothing else; the security-stamp check runs every 30 minutes and only on a stamp change. A `sessions` table in migration 5 does nothing unless it backs `ITicketStore`. Cookie defaults are `SameSite=Lax` and `SecurePolicy=SameAsRequest`, so on `http://localhost` nothing `security.md` specifies is emitted; Firefox has no Lax-by-default and sends an attribute-less cookie cross-site. There are four Identity cookies plus the antiforgery cookie, not one "session cookie", and the antiforgery cookie cannot be `Secure` on plain HTTP at all (C3-21).

## Blocking

**C3-1** · BLOCKING · reached by 2 seats: SRC-1, SEC-1 · SOURCE@dotnet/aspnetcore@v10.0.13:src/Antiforgery/src/AntiforgeryMiddleware.cs:25-51, src/Shared/HttpExtensions.cs:12-13, src/Http/Http.Extensions/src/RequestDelegateFactory.cs:397-402,1522-1527,2084-2092, src/Antiforgery/src/RequireAntiforgeryTokenAttribute.cs:7-10; DOCS@2026-10-21 anti-request-forgery ("Endpoint code always runs, even if token validation fails") · slice-03.md Spike J claim 2, build step 3 "Antiforgery per Spike J on every unsafe method", DoD 4; security.md "API" CSRF line.
The defect: `AntiforgeryMiddleware` considers only POST, PUT and PATCH (`IsValidHttpMethodForForm`), only endpoints carrying `IAntiforgeryMetadata { RequiresValidation: true }`, and on failure stores the outcome in `IAntiforgeryValidationFeature` and always calls `_next`. The only framework code that turns that feature into a 400 is the form-reading path of the request-delegate factory, which infers the metadata only for form-bound parameters. Every platform write binds JSON or reads a raw `text/csv`/`application/x-ofx` body, so `[RequireAntiforgeryToken]` or `app.UseAntiforgery()` on the `/api` group would make a missing or wrong token invisible, and a DELETE would never be validated. A step 3 built to the outline passes Spike J's "validation can cover every unsafe method" while every tokenless write still executes; the test that should catch it fails to fail.
What to do (SRC-1 and SEC-1, identical in substance): own the check. An endpoint filter on the `/api` group (or middleware after `UseAuthentication`) that, for every method other than GET/HEAD/OPTIONS/TRACE, calls `IAntiforgery.ValidateRequestAsync` (`DefaultAntiforgery.cs:143-180`) and returns a Problem response (SEC says 403, SRC says "a problem response"; the status is the builder's) on `AntiforgeryValidationException`; do not rely on `AntiforgeryMiddleware` or `RequireAntiforgeryToken`. Because `DefaultAntiforgeryTokenStore.cs:44-74` reads the header first and touches the form only for form content types, the `text/csv` upload needs no special case (SRC-1; RED P14 agrees). DoD 2's architecture test gains a second assertion: every unsafe-method endpoint carries the filter, DELETE included (SEC-1). Reword Spike J claim 2 to "validation *and refusal* can cover every unsafe method" (SEC-1), and have Spike J run a JSON endpoint, the raw-body upload and a DELETE with the header absent and see the refusal (SRC-1).
Severity: SRC placed it BLOCKING, SEC at MUST FIX before step 3. The broker keeps BLOCKING: the design's third write layer, as written, does not exist, and DoD 4 as written would not notice (C3-2). The fixes are the same; only the placement differed.
Cross-references: C3-2 (what DoD 4 can show), C3-22 (token bound to identity), C3-21 (antiforgery cookie and `Secure`), G-20.

## Must fix — at the step named

**C3-2** · MUST FIX, DoD 4 reworded before step 3 is designed · reached by 4 seats: RED-4, TST-1, SCO-1, BRW-6 (BRW at SHOULD FIX; the other three at MUST FIX, kept) · EXECUTED (slice 02's `CrossSiteBrowserTests`; BRW F7/F10 in Chromium 153 and Firefox 155) + `src/Api/Program.cs:37` (`UseCrossSiteWriteRefusal` before routing) · slice-03.md DoD 4, Spike J "The result decides".
The defect: a page on another `localhost` port is same-site, so the session cookie is sent (BRW F7: every cookie including `Strict`/`HttpOnly`/`Secure` arrived on fetch, form, `<img>`, iframe and navigation), but its write is stopped before antiforgery runs: a JSON or `text/csv` fetch is preflighted and never sent; a form or `no-cors` post arrives as a form content type and is `403` by `Sec-Fetch-Site: same-site` (`CrossSiteWrites.cs`, first in the pipeline) or `415` by the content-type allowlist. From `attacker.localhost` the `Strict` cookie is withheld and the refusal is a `401`, so a test that counts any non-2xx as success exercises none of the three layers (TST-1, BRW F8). A same-site page cannot, from a real browser, reach the antiforgery layer at all (RED P5(d)).
What to do (all four seats converge; TST-1's wording is the most complete and is taken): (i) integration, every unsafe endpoint: valid session cookie, `Sec-Fetch-Site: same-origin`, an accepted content type, and a missing, foreign or other-user token → refused, nothing written; and layer 2 alone: cookie and a valid token, `same-site` → `403`. (ii) The browser test keeps the same-site attacker with a signed-in context, records every request to the API, reads each refusal's body, asserts the expected `ProblemDetails.title` per case (not the status), asserts the cookie was sent (a `401` fails the test), and reads "nothing was written" from the signed-in page, not a bare client. (iii) Say plainly in DoD 4 and the assessment that the token's purpose is same-origin script and the "same-site" story is layers 1 and 2 (RED-4); or, if Kyle wants the token refusing in a real browser, a test-builder-only switch that drops layer 2 for one class, with a test that the published compose file does not carry it (TST-1, SCO-1: owner decision D12).

**C3-3** · MUST FIX before step 1 · reached by 7 seats: SEC-4, RED-5, OPS-4, SCO-2, SRC-11, A11Y-7, TST-3 (SEC/RED/OPS at MUST FIX; SCO and A11Y at SHOULD FIX; SRC at NOTE; kept at MUST FIX) · EXECUTED (`AppHost.cs` `WithDashboard(false)`; `README.md:106` "no dashboard"; `aspire-output/docker-compose.yaml` has no `OTEL_EXPORTER_OTLP_ENDPOINT`; `net localgroup docker-users` has one member; `ServiceDefaults/Extensions.cs` exports `ILogger` over OTLP when the endpoint is set) + SOURCE@…/Identity/Core/src/PasskeyHandler.cs:90-106,360 and SignInManager.cs:555-583 (SRC-11) · slice-03.md build step 1 ("First-run enrolment is an open design question"), DoD 3, DoD 7; README "Running it".
The defect, in four parts. (a) Channel: "a one-time setup code shown in the AppHost's console" exists under `aspire run` (terminal and dashboard console) and not in the published stack, where the only console is the `api` container's stdout: `docker compose logs`, Docker's log on the host disk, and (under `aspire run`) the OTel structured-log pipeline. (c) Atomicity: if enrolment creates the user and then registers the first credential in a second request, a closed tab leaves a user with no credential, which is either a lockout or a reopened race (RED-5); the spike's pattern creates the user on an anonymous options call, which would let any local process create the account (SRC-11). The enrolment is an `audit_event` with time and connection address, shown on first login (OPS-4). The harness must be able to set the code as a configuration value (`UseSetting` on the factory; `WithEnvironment` on the api resource in the test builder) with a test that the published compose file carries none (TST-3). Reword step 1's requirement from "must not leave a window" to "the window is bounded to [TTL] from first start, the code is single-use, and the claim is attested" (OPS-4), and state the honest limit: a process running as the same OS user can read it; that is `security.md`'s out-of-scope compromised host (SEC-4, OPS-4). The channel itself is the owner's decision (D2); the four seats' candidates and costs are there.

## Decisions for the owner

Each as the seats stated it, with the options and costs they gave.

**D1. TLS for the published stack** (OPS; Spike I's open question). (a) No TLS, the slice as written: costs nothing; depends on two browser carve-outs for `localhost`, both now EXECUTED (BRW); the app is reachable only as `localhost`; HSTS never. (b) Kestrel with the dev certificate in the container: `dotnet dev-certs` once, the PFX mounted, a second secret in `.env.Production`, a per-machine cert that expires yearly, port 8443, the HSTS trap becomes live. (c) mkcert or an owner-made CA: as (b) plus one more tool and a root in the Windows store. (d) A reverse proxy container (Caddy `tls internal`, nginx): one more image to pin, limit and restart; its root CA installed by hand; forwarded headers then genuinely needed with `KnownProxies` set to that container; two hops to debug; the shape `deployment.md` prescribes for LAN exposure. OPS's mark: (a) for this slice, with Spike I's proof recorded and the HSTS absence asserted; (d) for the day the API leaves loopback. BRW: "Spike I's 'does the published stack need TLS' can be answered no now, from EXECUTED evidence." SCO: "already deferred by the slice; agreed."

**D2. Where the first-run setup code appears** (OPS D2; SEC-4, RED-5, SCO-2, TST-3). All candidates are readable by the one account with Docker access (OPS-4). (a) Code in the log (`Console.Out` → `docker logs api`, and the dashboard console under `aspire run`): smallest; one line, a TTL, single-use, an audit event on use; stays in `docker logs` until rotation; SEC-4's version writes it via `Console.Out`, never `ILogger`, so it is absent from the structured-log capture DoD 7 asserts on; RED-5 accepts it only with a named, single exemption in the redaction test. (b) An Aspire secret parameter (`AddParameter("setup-code", secret: true)`): SCO-2's choice (user-secrets under `aspire run`, the git-ignored `.env` at publish, the channel the database password already travels; no console, no log line to redact); OPS marks it "worse": persisted, same readers, longer life, must be invalidated after use or it is a permanent second credential. (c) Enrolment by command (`docker compose run --rm api enrol` sets the password; the passkey is added from the browser after first login): a CLI mode in the Api and its tests; the published first run becomes two commands; no window in the browser at all; passkey-first enrolment is not possible this way. (d) A bind-mounted or named-volume file, mode 0600 (RED-5's preferred: "the version that needs no exemption in the redaction test"): a compose volume, Windows path quoting, one more thing `aspire deploy` must preserve; same window as (a). **D3. Where the data-protection key ring lives** (OPS D3; SEC-9, RED-10, SRC-10).
