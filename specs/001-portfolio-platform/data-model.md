PostgreSQL. Two schemas:

- **`app`** - the physical model. Written by ingestion, read by the API.
- **`reporting`** - views only. The sole surface user SQL and dashboards may
  read (D5, FR-6.2).

Nothing outside the ingestion pipeline writes to `app`. Nothing user-authored
reaches `app` at all.

## Conventions

**Identity.** `uuid` primary keys, generated by the application.

**Money.** `numeric(19,4)` with a separate `currency char(3)`. Never
`float`/`double` (FR-4.7).

**Time.** Two distinct concepts, never conflated:

- `as_of_date date` - the date a fact is *about* (the balance date).
- `observed_at timestamptz` - the instant the system *learned* it.

A balance restated a week later has the same `as_of_date` and a later
`observed_at`. Collapsing these loses the ability to reconstruct what was known
when, which is the whole point of an audit trail.

**Soft delete.** `deleted_at timestamptz null` (D12). Every `reporting` view
filters it. Nothing is physically removed.

**Provenance.** Every externally-sourced table carries (FR-4.3):

| Column | Type | Meaning |
|---|---|---|
| `source_system` | `text` | connector id, e.g. `mcp:monarch`, `api:plaid`, `import:csv`, `manual` |
| `source_id` | `text` | the upstream's stable identifier |
| `source_strength` | `provenance_strength` | how much the value can be trusted |
| `observed_at` | `timestamptz` | when it was learned |
| `ingest_run_id` | `uuid` | the run that produced it |

`source_strength` is an enum, strongest first:

```
statement    a document export or statement - the strongest routine source
api          a structured API or MCP response
derived      computed by this system from other stored values
scraped      read from a page rendered for humans
manual       hand-entered by the user
```

Recorded, never inferred (Constitution IV). A weaker source beats a null - the
recording of weakness is what makes it acceptable to use.

## Core tables

### `app.institution`

A financial institution. `id`, `name`, `kind` (bank, brokerage, retirement,
credit, mortgage, other), `website`, provenance, timestamps.

Generated data uses invented names (FR-11.5).

### `app.connection`

A configured link to a data source. One connection may serve many accounts.

`id`, `institution_id`, `connector` (`mcp` | `api` | `import` | `manual`),
`display_name`, `status` (`active` | `needs_reauth` | `revoked` | `error`),
`last_sync_at`, `last_error`, `cursor` (opaque, per FR-2.2), `credential_ref`,
timestamps.

**`credential_ref` is a pointer into the secret store, never a credential.** No
table in this schema holds a secret value (Constitution VII).

### `app.account`

`id`, `institution_id`, `connection_id`, `name`, `account_type` (checking,
savings, brokerage, retirement, credit, loan, mortgage, property, other),
`tax_treatment` (taxable, tax_deferred, tax_free, none), `currency`,
`opened_on`, `closed_on`, `is_closed`, provenance, timestamps.

- `(source_system, source_id)` unique where not deleted - the idempotency key
  (FR-4.2).
- **`closed_on` is load-bearing.** Once set, no balance may be written with a
  later `as_of_date`. Enforced in the pipeline *and* by a check constraint:
  Constitution III is too important to rest on application code alone.

### `app.account_balance`

The time series behind every net-worth figure.

`id`, `account_id`, `as_of_date`, `balance`, `available_balance`, `currency`,
`is_estimate`, provenance, `superseded_by` (`uuid` null), timestamps.

- Unique on `(account_id, as_of_date, source_system)` where not deleted.
- A restated balance **inserts a new row** and sets `superseded_by` on the old
  one. History is append-only; a correction is a new fact, not an edit.
- Check constraint: no row whose `as_of_date` exceeds the account's `closed_on`.

### `app.transaction`

`id`, `account_id`, `posted_date`, `authorized_date`, `amount` (signed;
negative is outflow), `currency`, `description`, `merchant_name`, `category_id`,
`pending`, `transfer_group_id`, provenance, timestamps.

- Unique on `(source_system, source_id)` where not deleted.
- `description` and `merchant_name` are **provider-authored text**: stored,
  escaped on output, never interpreted as instructions and never concatenated
  into SQL (FR-1.5).
- Amendment and removal upstream are handled by update and soft delete, keeping
  both the old and new states inspectable.

### `app.category`

`id`, `name`, `parent_id`, `kind` (income, expense, transfer, investment),
`is_system`, provenance. Hierarchical, self-referencing.

### `app.security` and `app.holding`

`security`: `id`, `symbol`, `name`, `security_type`, `currency`, `cusip`,
`isin`, provenance.

`holding`: `id`, `account_id`, `security_id`, `as_of_date`, `quantity`
(`numeric(28,10)` - fractional shares need more precision than money),
`cost_basis`, `market_value`, `currency`, provenance, timestamps. Unique on
`(account_id, security_id, as_of_date, source_system)` where not deleted.

### `app.pending_transfer`

Money reported as moving but not yet observed landing (Constitution V, FR-4.8).

`id`, `from_account_id`, `to_account_id`, `amount`, `currency`,
`reported_on`, `reported_source`, `landed_on` (null until observed),
`landed_balance_id` (the balance row that evidences it), `cancelled_on`,
`cancelled_reason`, timestamps.

`landed_on IS NULL` means **unverified, not zero**. Any aggregate including such
a row is conditional and must be labelled so wherever displayed. `landed_on` and
`cancelled_on` are mutually exclusive - one terminal state, enforced by
constraint.

### `app.ingest_run`

Immutable (FR-4.6). `id`, `connection_id`, `started_at`, `finished_at`,
`status` (`running` | `succeeded` | `failed` | `partial`), `trigger`
(`scheduled` | `manual` | `webhook`), counts of records created, updated and
soft-deleted, `error_detail`, `environment`.

Never updated after completion, never deleted. Every sourced row points back to
one of these, so any figure can be traced to the run that produced it.

### `app.audit_event`

Append-only. `id`, `occurred_at`, `actor`, `event_type` (credential use,
credential rotation, data mutation, report execution, projection run, export,
login), `subject_type`, `subject_id`, `detail` (`jsonb`), `environment`.

`detail` MUST NOT contain secret values. A test asserts this against known
secret-shaped patterns.

## Policy and constants

### `app.constant`

External reference values - contribution limits, thresholds, bracket
boundaries. Three legal states, and the third is the interesting one:

1. **Sourced** - `value` is not null, `source` names where it came from.
2. **Gated** - `value` is null, `gated_on` names the action that would resolve
   it. Null means UNVERIFIED (Constitution II).
3. **Working assumption** - `value` is not null, `is_assumption` is true,
   `source` opens with an explicit banner marking it as unsourced, and
   `gated_on` names an open action dated before any irreversible step.

State 3 exists because a null cannot be planned against, and pretending
otherwise leads to worse outcomes than an openly-labelled assumption. It is
deliberately constrained: a check constraint requires that
`is_assumption = true` implies a non-null `value`, a banner-prefixed `source`,
and a non-null `gated_on`. **No terminal action may depend on a state-3 value** -
no projection feeding an irreversible decision, no hard-deadline calculation.
Enforced at validation time, and tested.

Columns: `id`, `key`, `value`, `unit`, `tax_year`, `source`, `is_assumption`,
`gated_on`, `varies_by`, `note`, timestamps.

### `app.policy_rule`

The user's own investment policy, as data rather than code.

`id`, `rule_key`, `rule_type` (target, band, floor, threshold, admissibility),
`value`, `unit`, `applies_to`, `is_gated`, `gated_on`, `source`, `review_by`.

Drives target-versus-actual dashboards and rule-evaluation projections. A gated
rule is reported as unevaluable - never silently skipped, because a rule that
vanishes when it cannot be checked is worse than one that reports it cannot be
checked.

## Projections

### `app.projection_model`

Registry mirror of the code-side plugins. `id`, `model_key`, `version`,
`title`, `description`, `input_schema` (`jsonb`), `output_schema` (`jsonb`),
`registered_at`, `is_active`.

`input_schema` is what the UI renders from (FR-8.4).

### `app.scenario`

`id`, `name`, `description`, `model_key`, `parameters` (`jsonb`), `version`,
`parent_scenario_id` (for variants), `created_at`, `updated_at`.

Versioned: editing a scenario creates a new version, so a stored run always
refers to the exact parameters that produced it.

### `app.projection_run`

`id`, `scenario_id`, `scenario_version`, `model_key`, `model_version`,
`status` (`succeeded` | `refused` | `failed`), `result` (`jsonb`),
`refusal_detail` (`jsonb` - which inputs were unresolved, and why),
`input_hashes` (`jsonb` - one sha256 per resolved input), `engine_version`,
`ran_at`, `is_stale`.

**A refusal is a stored, first-class outcome**, not an error log line
(Constitution II). "This could not be computed, and here is exactly what is
missing" is frequently the most useful answer the system can give.

`is_stale` is recomputed when any hashed input changes. Prior runs are never
rewritten (Constitution VI).

### `app.saved_report`

`id`, `name`, `description`, `sql_text`, `parameters` (`jsonb` - declared
parameters with types and defaults), `created_at`, `updated_at`, `last_run_at`.

`sql_text` is stored verbatim and executed **only** on the restricted
reporting connection. Parameters are bound at execution; never interpolated
(FR-6.4).

## The `reporting` schema

Views only. A separate role holds `USAGE` on this schema and `SELECT` on these
views, and nothing else anywhere (D5).

| View | Contents |
|---|---|
| `v_account` | accounts with institution, type, tax treatment, open/closed, provenance |
| `v_balance_daily` | balances by account and date, superseded rows excluded, **no gap-filling** (Constitution III) |
| `v_net_worth_daily` | assets, liabilities and net worth by date, with a `has_conditional_money` flag |
| `v_transaction` | transactions with account, category and merchant resolved |
| `v_holding` | holdings with security detail and market value |
| `v_allocation` | current allocation by asset class, with look-through where available |
| `v_allocation_vs_policy` | allocation against policy targets and bands; gated rules marked unevaluable |
| `v_cash_flow_monthly` | income, expense and transfer totals by month and category |
| `v_pending_transfer` | unlanded transfers - the reason an aggregate is conditional |
| `v_ingest_run` | sync history and outcomes |
| `v_constant` | constants with their state (sourced, gated, assumption) |

Rules for every view:

1. Soft-deleted rows excluded.
2. No forward-fill, no interpolation, no gap-filling. A series that stops, stops.
3. Any aggregate that could include unlanded money carries a flag saying so.
4. Column names and meanings are documented in the UI (FR-6.6) and are a
   **stable contract** - physical tables may change beneath them; a view's
   column may not change meaning without a version.

## Migration from the file-based system

The originating system's YAML files map onto this schema as an **import format**,
not as content to be copied. No real values travel.

| Source file | Target |
|---|---|
| `accounts.yaml` (slug, institution, type, closed, last sync) | `institution`, `account`, with `source_system = 'import:yaml'` and `source_strength = 'manual'` |
| `history.yaml` (dated net-worth series; per-account balances) | `account_balance`, `as_of_date` from the series date |
| `allocation.yaml` (net worth, assets, liabilities, mix) | derived - recomputed from balances, never imported as a figure (Constitution I) |
| `ips.yaml` (targets, bands, floor tiers) | `policy_rule`, gated entries importing as `is_gated` |
| `constants.yaml` (sourced or null + gated_on) | `constant`, all three states preserved |
| `transfers` (reported, landed, cancelled) | `pending_transfer` |
| `models/*.py` | `IProjectionModel` implementations; not data |

`allocation.yaml` is the instructive case: it is a *derived* view in the source
system, and importing its totals as stored figures would violate Constitution I.
The importer takes balances and recomputes. If the recomputed total disagrees
with the file's, that disagreement is a finding worth surfacing - not something
to paper over by importing the file's number.
